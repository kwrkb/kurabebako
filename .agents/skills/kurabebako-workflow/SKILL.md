# kurabebako の Codex 作業手順

## 適用と参照先

このファイルは Codex 向けの制作・運用手順。記事の仕様やフェーズ判断は定義しない。
共通規約は [AGENTS.md](../../../AGENTS.md)、詳細な記事の型は
[CLAUDE.md](../../../CLAUDE.md)、目的は [VISION.md](../../../VISION.md) を参照する。
Claude 用の `.claude/`、コマンド、画像生成スクリプト、定期処理をこの手順に合わせて変更しない。

以降のパスはサイトのリポジトリルート基準。`desk` は隣の `../kurabebako-desk/` を指す。
ここには再利用する手順だけを置く。調査素材・プロンプト・試作品・観測値は private の desk に残す。

## 1. 作業の範囲と出力先を決める

AGENTS.md の開始確認を行い、サイトと desk の変更状態・参照した Git HEAD を把握する。
依頼された工程だけを実施する。図の依頼から記事公開へ進むなど、作業範囲を広げない。

| 依頼 | 作業範囲 |
| --- | --- |
| Codex の定期処理 | `desk/routines/codex/README.md` と該当プロンプトを読み、その実行フォルダ内だけで作業する |
| 比較案・試作・レビュー、Claude と並行する制作 | `desk/reports/codex/<処理ID>/<実行時刻>/` に案と報告を残す。手動の処理IDは `manual-<slug>` など対象が分かる名前にする |
| ユーザーから依頼された記事編集・採用反映 | 指定された共有ファイルを更新する。既存の依頼で許可された範囲は再確認しない。公開はその依頼に含まれるか別に判断する |

実行時刻は日本時間の `yyyy-MM-dd-HHmmss-fff`。同名なら識別子を足し、過去の出力を上書きしない。
案作成では共有記事・台帳・ログ・Git index/refs を更新しない。共有 checkout でビルドやプレビューも起動しない。
定期処理で禁止された Git 操作を、worktree 作成や同期のために実行しない。

共有ファイルへの反映直前には対象を読み直し、開始時からの差分を確認する。
同じ対象への他作業の更新を見つけたら、その反映を止めて担当範囲を調整する。変更状態が空でも排他の保証とは扱わない。
専用フォルダで案を完成させる作業は継続できる。
desk への書き込み権限がない場合は必要な権限を求め、private の資料を public 側へ代替保存しない。

## 2. 企画・調査・実行証跡を揃える

- 候補選びでは `desk/backlog.md`、ネタ探しでは `desk/neta-method.md` と `desk/neta-log.md` を読む。
- 次に書く記事と状態は backlog 冒頭の「現在の作業ステータス」で確認する。ネタ探しは `desk/neta-log-index.md` 全体とログの直近7日を読み、索引から必要な過去の記録を辿る。
- 対象の `desk/research/<slug>/` と `desk/lab/<対象>/README.md` を読み、比較の条件と未確認事項を整理する。
- 料金・無料枠・制約は公式ページを実際に取得して確認する。URL、確認日、単位、適用条件を残す。
- 既存の実行証跡と今回調べた仕様を区別する。主役を実行区分で裏付けられなければ公開可能とは判定しない。
- 新規の実行検証が依頼の範囲内なら、lab 手順と `desk/teardown.md` に従って行う。秘密情報は 1Password から注入する。
  定期処理では新規実験・外部書き込みを行わず、必要な検証を提案する。

案作成で得た追加調査や検証計画は今回の実行フォルダへ置く。共有の research・backlog の更新は採用反映の工程で行う。
依頼された新規実験で外部環境を作る場合は、その実験の書き込み範囲で teardown の記録と撤収まで行う。

## 3. 本文と図の内容を固める

`archetypes/posts.md` と関連する shortcode を読み、共通の記事の型で作る。
案作成では実行フォルダに `article/<slug>.md` を置き、`draft = true` とする。
共有サイトの新記事は `hugo new content posts/<slug>.md` で作る。既存記事の修正依頼なら、依頼された公開状態を維持する。

表の数値を先に揃え、本文では条件ごとの選び分けを書く。図ごとに「何を理解してもらうか」を一文で決める。
図の数値・分岐条件は本文と同じ根拠から取り、図だけに新しい結論を加えない。
広告と内部リンクは共通規約に従う。既存記事から追加するリンクは、案作成では配置案として残す。

## 4. 図・OGP を用途別に作る

| 用途 | 作り方 | 確認点 |
| --- | --- | --- |
| 料金・上限・実測値 | 既存の `bars` | 単位を揃え、表と同じ数値・出典を使う |
| 用途別の判断フロー | SVG をコードで作り `svg` shortcode で挿入 | 分岐と文言を照合し、`currentColor`・塗り `none` を守る |
| OGP | 内蔵の画像生成を使用 | 既存の配色・モチーフ・文字の規約を読み、出力を目視確認する |
| 操作・実行結果の証拠 | 実際の画面キャプチャやログ | 生成画像を実行証拠にしない。秘密情報が写らない対象・範囲で取得する |
| 本文に追加したい概念イラスト | まず独立した提案として試作 | 現在の本文図は2種類。追加採用には共通の図の規約変更が必要 |

SVG は Codex でも使う。数値と構造は編集可能なコードで管理し、OGP の絵づくりに画像生成を使う。
本文の図に会話用の可視化や Mermaid、CDN の JS を持ち込まない。

OGP を作るときは、利用可能な `imagegen` スキルを読み、以下を行う。

1. `desk/images/README.md` と対象・関連する `<slug>.md`、採用済み画像を確認する。
   現行の寸法・配色・ワードマーク等を引き継ぐ。別の画風は試作として区別する。
2. 用途、記事のモチーフ、構図、正確な文字、避ける要素をプロンプトにする。
   参照するローカル画像は先に表示して確認する。
3. 内蔵 `image_gen` で生成・編集する。モデル名や出力先引数を推測しない。
   内蔵ツールが使えない場合は未生成と報告し、未依頼の CLI/API や Claude 用スクリプトへ切り替えない。
4. 出力を見て、文字・構図・元の規約との一致を確認する。必要な修正を指定して再確認する。
   指定寸法と実寸を照合し、ファイル形式だけを拡張子で偽装しない。
5. ツール既定の保存場所から今回の実行フォルダへ成果物をコピーし、プロンプト・生成日・利用した手段を同名の `.md` に残す。
   採用反映では desk の画像作業場に制作記録を残し、サイトには採用画像だけを配置して記事の参照を更新する。

ツール既定の保存場所は一時的な受け取り先。記事や試作からそこを直接参照しない。
定期プロンプトのツール・出力制約に合わない生成は行わず、画像案と未実施理由を報告する。

## 5. ビルドと表示を確認する

案作成では必要なサイト入力だけを実行フォルダの `site-copy/` にコピーする。
`.git`、資格情報、既存の生成物・依存ディレクトリをコピーせず、出力とキャッシュを今回のフォルダ内に向ける。
記事案・SVG・画像をコピー内の採用予定位置へ置いて検証する。共有サイトでは実行しない。

採用反映では対象 checkout で AGENTS.md の検証手順に従う。
どちらも Hugo の版を `build.sh` と揃え、本番条件のビルドと、完成した draft の検査を区別する。
本番ビルドの成功だけで、除外された draft を検証済みとしない。

本番条件は検証対象のルートで `node build.js` を実行する。案作成では必ず `site-copy/` 内のコピーを使う。
完成した draft は同じルートで `hugo --buildDrafts --gc --minify --destination .cache/draft-check` を別に実行し、
案作成時の Hugo キャッシュもコピー内に指定する。`build.js` は追加引数を転送しないため、draft 用フラグを渡して済ませない。
表示検査は `npm run test:layout`、draft も含める場合は `npm run test:layout -- .cache/draft-check` を使う。
案作成では `tests/layout-check.js` と `package.json` もコピーに含め、一時ブラウザプロファイルの保存先（Windows の `TEMP` / `TMP`）も今回の実行フォルダ内に設定する。
この検査は横はみ出しだけを見る。色・余白・図の見た目の確認の代わりにはしない。ツール不足や実行失敗は未検証として報告する。

ブラウザで該当ページを開き、スマホ幅・明暗テーマの表、図、PR、リンク、OGP 設定を確認する。
ブラウザ操作は利用可能な手段のスキル・ツール規約に従う。表示できなければ未確認と記載する。
単位・出典・実行区分・結論はビルドと別に照合する。

## 6. 報告・採用反映・公開後の更新

案作成の `report.md` には、対象と入力の版、成果物の相対パス、採用先、検証結果、未確認事項、必要な変更をまとめる。
処理中に入力が変わった場合は照合し直すか、整合未確認と記載する。
既存の実行フォルダを更新せず、追加案は新しい実行フォルダに残す。

採用反映を依頼されたら、最新の共有ファイルと比較して必要な変更だけ適用し、再検証する。
開始時点のコピーで共有ファイル全体を置き換えない。記事・画像・関連リンクと必要な desk の記録を揃える。
終了前の差分確認と Git 操作、公開判断は AGENTS.md に従う。定期処理の案作成は自動でこの工程へ進めない。
`npm run push:site -- --dry-run` も共有 checkout でビルドと検証を行うため、定期処理の読み取り確認には使わない。

公開後の出典再確認・観測・依存調査・改善提案は `desk/routines.md` と該当する Codex プロンプトへ接続する。
スケジュールや登録済みプロンプトは、この手順を作成・更新しただけでは変更しない。
